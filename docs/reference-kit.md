# Reference kit: the tools and editors on awesome-love2d

Looked at on 2026-11-15, asked to check every tool and editor on [awesome-love2d](https://github.com/love2d-community/awesome-love2d) and keep what could improve JoyrIDE. Each was cloned shallow (`--depth 1`, no submodules) into a scratch folder and **read, never run**; the READMEs, file lists and a few source files were the evidence. Where this page says what a tool does, that is what its README and files show; "for JoyrIDE" lines are judgement and say so.

**Licence rule for this kit.** JoyrIDE is MIT with no GPL, AGPL or LGPL (`CLAUDE.md` rule 2). A tool under **GPL, or with no licence file, gives ideas only: no code, no data, no text is copied.** MIT, zlib and CC0 code can be reused, with its notice in `NOTICE`, once the maintainer agrees (a vendored file needs rule 11's decision recorded). Nothing here has been copied into the repository.

## What JoyrIDE can take, in the order I would take it

1. **Windows icons: port `love-pe`'s method** (MIT). `ROADMAP.md` says the desktop exporters do not generate `.ico` or `.icns` yet. love-pe does the hard part in 927 lines of Lua with no native code: it parses the DOS and PE headers, the section table and the resource tree, replaces or *patches* the `ICON_GROUP` in place (patching keeps the file valid; rebuilding the whole resource table is the riskier path its README warns about), and writes the file back. A Rust version inside `joyride-core` would give a fused Windows build the game's own icon from any host, with no Wine and no Windows tool. Measure it against a real `love.exe` from the LÖVE release (the same discipline as `tests/e2e_love.rs`) and check the result still starts under Windows when someone with a PC can try it: **untested here**. Its checksum caveat (it leaves the PE checksum at 0) is fine for LÖVE's own exe.
2. **A generated CI workflow: read `love-build`.** It shows the packaging steps in the open: zip the project into `application.love` (excluding `.git*`), copy the user's own `Info.plist` over LÖVE's if there is one, download LÖVE's per-platform archives, zip each result, and (optionally) bundle LuaRocks dependencies by prepending a module loader to `main.lua`. JoyrIDE already does the packaging itself (`pipeline`); what is worth taking is the idea of **exporting a `.github/workflows` file that builds the same targets on the person's own GitHub** (no accounts of ours, rule 1, through the `gh` route that exists). Its Docker approach is not needed.
3. **Version choice: Flirt's idea, already ours.** Flirt reads the `version` a game's `conf.lua` (or `.love` archive) asks for, finds installed binaries by running each with `--version`, keeps that list in `~/.config/flirt/conf.lua`, and runs the matching one. JoyrIDE's toolchain core already does this per project (`love.toml`, 11.5 and 12.0). Nothing to take; confirms the design. Its "stable versus prerelease" split is worth a line in the version picker.
4. **Docs data: `love-api` is the schema `docs.rs` already uses, but it carries no licence.** It is a Lua table of modules, functions, variants, arguments, returns and descriptions, copied by hand from the LÖVE wiki, 11.5 only. Do not vendor it. `ROADMAP.md` lists "the `love-api` 11.5 JSON for the docs drawer" as to do: either ask the author (rm-code's `love2d-community/love-api`) for a licence, or generate the data from the wiki's own content under its licence, or from the real binaries (`scripts/love-api-diff.py` already measures them). Its wiki scraper lives in `wiki_scraper/`.
5. **Shadertoy import: `LoveShaderConverter`'s rules** (MIT, 2016). The whole tool is one C++ file of string replacements: `float` becomes `number`, `samplerXX` becomes `Image`, `texture2D` becomes `Texel`, the `iResolution`, `iGlobalTime` and `iChannel` uniforms become `extern` declarations, and a generated `effect()` calls `mainImage(color, fragCoord)`. It also declares `iMouse`, but it has no `iTime` (Shadertoy's newer name for `iGlobalTime`) or `iFrame`, only one `iChannel`, and it edits in place with a `.bak`. A small Rust version in the shader support would be a clean-room job from this description (the replacements are facts, not expression), measured against real LÖVE 11.5 and 12.0, and must not copy a converted shader's licence away (Shadertoy shaders carry their own).
6. **Atlas packing in the Asset Library: `Export-TextureAtlas`'s options** (MIT). Its flags show what people ask of an atlas: maximum size (default 16384), padding, extrude, fixed cell size, `-removeFileExtension`, several inputs and outputs, and **user templates** (Lua or JSON via lustache) so the output matches the engine. `asset-core` has no atlas export yet; a generator panel should offer padding, extrude and a Lua and JSON template, and keep to the deterministic and licence-confirmed rules (`docs/asset-library.md`).
7. **Particle generators: take the editors' feature sets, not their code.** Hot Particles (no licence file: ideas only) exports a Lua module with one entry per particle system (`system`, `kickStartSteps`, `kickStartDt`, `emitAtStart`, `blendMode`, `shader`, `texturePreset` or `texturePath`, emitter offset) plus a clipboard template; that module shape is a good target for a JoyrIDE particle generator because it round-trips the things `love.graphics.newParticleSystem` cannot save by itself (kick-start, blend, shader). ParticleEditor (MIT) saves JSON and edits several systems at once; particle-system-playground (CC0) is the small model: click to place the emitter, drag a number to change it, drop an image to set the texture. The Asset Library's generators must stay seeded and deterministic (rule 11), so a particle generator records its recipe and seed.
8. **TypeScript and MoonScript: do not build in yet, remember the shape.** `love-typescript-definitions` (MIT) gives `.d.ts` files for 11.5, used with TypeScriptToLua; `selene` (MIT) runs `.moon` files directly by hooking the loader instead of compiling; `lovelier` reloads on change and compiles MoonScript on the fly. For JoyrIDE this is a later question: a TypeScript or MoonScript project would need its transpiler as a toolchain entry, a source map for the console's line numbers, and a rule that "the user's source is never mutated" still holds for generated Lua. The definitions repository is also a map of the LÖVE API's shape that can be compared against our measured tables.
9. **Editor design: `text2.love` and `Polywell` are GPL, so lessons only.** text2.love is a deliberately small editor (1200 lines, zero dependencies) that is tested against a long real text and documents its shortcuts, its untested keyboard layouts and its unsupported cases (grapheme clusters, right-to-left); the habit worth copying is writing the known gaps down next to the shortcuts. Polywell's idea is **in-game coding**: an editor inside the running game, for the person's tighter feedback loop. JoyrIDE's answer is the language server and Run with live console; an in-game REPL overlay would be new and is for the maintainer to decide.
10. **Project manager: `lovely-engine` is the closest cousin** (MIT, Linux, built on love-nuklear): a GUI to create and manage LÖVE projects from a template, with plugins (a button launching the lite editor in the project folder; a visual-novel scripting plugin) and a library set in the template. JoyrIDE already has projects, a curated library list and samples. Worth checking against JoyrIDE: a **"launch in another editor" button** (lite, VS Code, Zed) for the people who do not want Monaco, and a project template that already contains a chosen library set. Both fit rule 13 only as actions, not as new UI looks.
11. **Native file dialogs: `nativefiledialog` solves the open and save dialog problem the roadmap lists,** but as a compiled C library (zlib) with a Lua binding that is only a fork. JoyrIDE's own app is Tauri, which has native dialogs already, so this matters only inside a *game's* own code; it stays a note next to the existing "native open and save dialogs" item. `love-imgui` (compiled, last commit 2019) is superseded by the curated `cimgui-love`.

## BBEdit and TextWrangler, for JoyrIDE's editor

Looked at 2026-11-15. **TextWrangler is gone:** Bare Bones released BBEdit 11.6 in 2016 with a *free mode* that has TextWrangler's whole feature set, and retired TextWrangler in March 2017, so everything TextWrangler did is now "BBEdit, unlicensed". There is no newer TextWrangler to check; BBEdit is the reference. BBEdit is proprietary and paid ($60; free mode is unlimited), so this section takes **behaviour and ideas only**: no code, no text, no strings, and no BBEdit name in anything a person sees.

What was read: Bare Bones' feature pages (text, search, programming, display, file handling), the free-mode comparison chart, the *Language Server Protocol Support in BBEdit* notes, the BBEdit 16.0 release notes, and 9to5Mac's report of the 16.0 launch. **Not read:** the 16.1 pre-release notes, the user manual, or BBEdit itself (not installed here). The 16.0 notes page printed no date; 2026-05-21 is 9to5Mac's launch date.

### The measured gap: the language server does more than JoyrIDE asks of it

This one is a fact about our own code, not a judgement. The bundled `lua-language-server` was started here and asked what it supports (initialize reply). It offers references, rename (with prepare), code actions (quick fix, refactor rewrite and extract), document symbols, workspace symbols, document highlight, folding ranges, semantic tokens (full), inlay hints, implementation, type definition, code lens, range and on-type formatting. `src/lib/lsp.ts` registers only completion, hover, signature help and definition, plus diagnostics, while `src/monaco-setup.ts` **already loads Monaco's UI for rename, reference search, code actions, document symbols, linked editing, inlay hints and semantic tokens.** Those parts of the editor have nothing feeding them. BBEdit's LSP page is the checklist of what a good editor does with such a server: completion, signature help ("Show Parameter Help"), diagnostics in the text, the line-number bar and a count in the status bar, **Go to Definition and Declaration, Find References, Find Symbol in Workspace, Rename Selected Symbol, Code Actions with a Fix button**, formatting through the server, and (since 16.0) semantic-token colouring that outranks its own keyword colouring where the server supplies it.

### What BBEdit does that is worth a look, in the order I would take it

1. **Wire the rest of the language server** (above): references, rename, code actions, document and workspace symbols, semantic tokens. Cheapest, biggest, and all are in the server already. Keep rule 9: each reachable by a hotkey and named for VoiceOver. BBEdit shows server status in the editor (a ready, disabled or missing colour in its Languages list); JoyrIDE's status bar already shows the server's state, so the new part is a *count* of problems and a "fix" action.
2. **A symbol list for the open file ("function navigation").** BBEdit's function popup is its main way around a file, built from the language module, not the server. JoyrIDE can feed Monaco's loaded outline (`documentSymbols`) from the server's document symbols, and offer "go to symbol in project" from workspace symbols. Needs a place in the 48 by 25 layout: a panel page, never a scrolling pane (`docs/text-mode-ui.md`).
3. **Search that matches BBEdit's multi-file search.** JoyrIDE's Find in files has **match case only** (`src/components/Search.tsx`). BBEdit's has PCRE patterns (the free mode too), a results browser you can open each hit from, file filters, skipping Git-ignored files (16.0 does this by default for speed), "extract found text into a new document", and a live search that highlights as you type. First steps: regex and whole-word switches, ignore `.gitignore`d folders, and a results list. Grep patterns need a cheat sheet in the panel; BBEdit ships "Grep Cheat Sheets" for that reason.
4. **A Text menu of line and selection tools, as hotkeys.** BBEdit's Text menu is its daily tool: sort lines, process duplicate lines (16.0 can prefix each result with how many it removed), process lines containing a pattern, prefix and suffix lines, add or remove line numbers, change case, shift left and right, hard wrap, entab and detab, normalize line endings, zap gremlins (invisible or stray control characters), exchange characters or words, column operations on CSV or TSV. **Monaco already has many of these loaded** (`linesOperations`: sort, remove duplicate lines, trim trailing whitespace, join, upper, lower and title case, copy lines; `indentation`: tabs or spaces; `transpose`; `multicursor`), but whether JoyrIDE exposes them by a hotkey was **not checked** (only that the modules are imported). A page of the bottom window's PANELS could list them with their letters. The ones Monaco lacks and a Lua programmer would use: normalize line endings, zap gremlins (Monaco's `unicodeHighlighter` is loaded and does the *showing*, not the removing), process lines containing, prefix and suffix lines, and rectangular selection (Monaco has column selection by gesture; check it works by keyboard).
5. **Show invisibles and the current line, as options.** BBEdit lists "display invisible characters", "tab stops and highlight current line", line numbers and "color-keyed window appearance". 16.0 also marks private-use-area surrogate pairs with a red mark, because they have carried malicious code: that is the same job as Monaco's loaded `unicodeHighlighter`, worth keeping on and testable (paste a file with a bidi override and see it flagged). In text mode these are colour and character options only (rule 13).
6. **Per-project colours.** 16.0 lets a project or a notebook override the colour scheme so windows are told apart. JoyrIDE's only appearance option is the palette (rule 13); a *per-project palette choice* would fit, stored in the project's `.joyride/` folder, not a new theme.
7. **EditorConfig, and the Git-ignore habit.** BBEdit's free mode has built-in EditorConfig support, and 16.0's new projects get a `.gitignore` for ephemeral and user-specific files. JoyrIDE could read `.editorconfig` (indent, final newline, trailing whitespace; Monaco's `insertFinalNewLine` is loaded) and write a `.gitignore` that already lists `.joyride/` caches when it makes a project. Check both against what `files.rs` and project creation already do before adding.
8. **Per-language settings.** BBEdit lets each language have its own tab width, soft wrap and server. JoyrIDE edits Lua, plus `love.toml`, JSON and GLSL: a small per-extension table for indent and wrap would stop a shader inheriting Lua's settings.
9. **Compare two files, and compare to the last saved or committed version.** "Find Differences" (with line-level highlights and apply-change) and "Compare to Base / Head" are the BBEdit feature people use most after search. Monaco's diff editor is already loaded (`diffEditor.contribution`); a hotkey for "compare to disk" and "compare to Git HEAD" (through `git`, rule 5) needs only a pane.
10. **Smaller ones.** *The same document in two windows* (BBEdit shows edits in every window at once; whether JoyrIDE can split a document was not checked). *Notebooks and scratchpad* (a per-project notes file that is searchable; the licensed tier only). *Worksheets and shell worksheets* (a text file you can run lines of; Run and the console cover the LÖVE case). *Open File by Name* (a hotkey to open a project file by typing part of its name; I found no such command in `Editor.tsx` or the file tree, which does not prove there is none). *A vi mode* (added in 16.0; Monaco's own build has none, and a third-party add-on would need its licence checked first: a decision, not a default). *LLM worksheets* (16.0 streams from model providers): **not for JoyrIDE** under rule 1 (no accounts or network use of ours).

### What not to take

- BBEdit's **text factories, Automator filters, AppleScript and FTP/SFTP site tools** are Mac-only or out of scope; none is a LÖVE job.
- **In-image text search** (16.0, uses the OS's text recognition) is clever but off the path for a LÖVE editor.
- Anything that sends text off the machine: BBEdit's own notes say a language server runs locally and sends nothing; keep it that way (rule 1).
